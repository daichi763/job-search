# AI検索（新方式）— フェーズ1：検索エンジン本体と評価コマンド

求人DB（hub）の**全求人を母集団**として、求職者に合う求人を探す新しいAI検索です。
媒体に毎回ログインする旧方式（worker）とは別に動きます。フェーズ1は**評価コマンドだけ**なので、稼働中の画面やAI検索には影響しません。

## 仕組み（4段階）

| 段階 | やること | モデル |
|---|---|---|
| 1. 理解 | 要望と書類の経歴から「探し方（切り口）」を3〜6個作る。**王道**（経験そのまま）・**発展**（キャリアアップ）・**意外**（人の手では思いつきにくい隣接領域） | 優秀モデル |
| 2. 絞り込み | 画面の確定条件（勤務地・年齢・年収・雇用形態・働き方・学歴・性別・紹介済みの除外）で**全求人**から母集団を作り、切り口のキーワードで関連の強い順に並べる | なし（DBのみ・数秒） |
| 3. 一次審査 | 関連の強い求人（標準2,000件／徹底8,000件／全件）を安価なモデルで5段階評価 | 高速モデル |
| 4. 精査 | 有望な求人（提案件数×6）を**求人票の全文**で審査。必須要件を1つずつ「○満たす／×満たさない／？不明」で判定し、根拠を付ける。**2段階**：高速モデルが全件を予備判定し、上位（提案件数×2）だけ優秀モデルが最終判定する | 予備判定＝高速モデル／最終判定＝優秀モデル（「最高精度」なら最上位モデル） |

### 応募条件を満たさない求人が高得点になる問題の対策
- 以前は応募条件の**先頭300字**しかAIに渡していなかった。今回からは**全文**（最大3,500字）を渡す
- 必須要件ごとの判定結果から、**最終点はプログラムで決める**（AIの点数をそのまま使わない）
  - 必須要件に「×」が1つでもある → **55点が上限**。提案には入れず「参考（内容は合うが要件不足）」に回す
  - 書類があるのに必須要件を確認できない（？）→ **84点が上限**（応募前の確認事項に表示）
- 学歴・性別の条件は、AIではなくプログラムで機械的に判定する

### 提案の幅
- 一次審査の対象は、切り口ごとの上位を均等に入れ、さらに職種ごとに少しずつ入れる（キーワードに当たらない職種の取りこぼしを防ぐ）
- 精査の対象も切り口ごとに枠を取る（似た求人だけで枠が埋まらないように）
- 提案の上位2割までは、王道以外（発展・意外）で75点以上の求人を入れる
- 同じ会社の同じ募集（媒体違いなど）は1件にまとめる

## モデルの設定（`hub/.env`）

未設定なら次の既定値を使います。使えないモデル（契約していない等）は自動で次の候補に切り替えます。

```bash
HUB_AI_MODEL_SMART=gpt-6.1-sol       # 理解・書類の読み取り・精査の最終判定・推薦文
HUB_AI_MODEL_TOP=gpt-6-astra         # 「最高精度」を選んだときの精査
HUB_AI_MODEL_FAST=gpt-6-luna         # 一次審査（大量）・精査の予備判定
HUB_AI_FALLBACK_MODELS=gpt-5.5,gpt-5.2,gpt-5        # 優秀モデルが使えないときの候補（順番に試す）
HUB_AI_FALLBACK_FAST_MODELS=gpt-5-mini,gpt-5-nano   # 高速モデルが使えないときの候補
# APIキー・接続先は worker/.env の OPENAI_API_KEY / OPENAI_BASE_URL をそのまま使う
#   別のキーにしたい場合だけ HUB_AI_API_KEY / HUB_AI_BASE_URL を指定

# 件数などの調整（任意）
HUB_AI_SCREEN_STANDARD=2000   # 標準: 一次審査の件数
HUB_AI_SCREEN_DEEP=8000       # 徹底: 一次審査の件数
HUB_AI_DEEP_MAX=120           # 精査の最大件数
HUB_AI_CAP_UNMET=55           # 必須要件を満たさない求人の上限点
HUB_AI_CAP_UNKNOWN=84         # 必須要件を確認できない求人の上限点
HUB_AI_MIN_SCORE=60           # 提案する最低点
HUB_AI_CONCURRENCY=8          # 1件の検索の中で、OpenAI に同時に送る数
HUB_AI_PRE_CONCURRENCY=8      # 予備判定（精査の1段目）で同時に送る数。上げると速くなる（精度は変わらない）。利用制限に当たっても自動で待ってやり直す
HUB_AI_MAX_PARALLEL=3         # 同時に実行できるAI検索の数（超えた分は順番待ち）
```

### 費用を抑える仕組み（2026-10 改訂）
初回の実データ評価（書類なし・提案20件）で約145円。その大半（約85%）は「精査」で、特に**精査した80件すべてに推薦文を書かせていた**ことが原因でした。

| 変更 | 精度への影響 |
|---|---|
| 精査を「判定」と「推薦文」に分割し、推薦文は**提案に残った求人だけ**書く | なし（判定の内容・読む求人票の範囲・件数は以前と同じ。推薦文には判定結果と求人票を渡す） |
| 一次審査は25件ずつまとめて送る（以前は20件） | ほぼなし（送る求人の情報量は以前と同じ） |
| 精査を途中で打ち切る | **あり**。検証で、精査の最後のほうに最高点の求人が出ることがあり、途中で止めると上位を取りこぼした（提案10件中3件、上位5件中2件が入れ替わった）。そのため**使わない**（第2回改訂で economy からも外した） |

### モデルの使い分け（2026-10 第2回改訂）
費用の大半は「精査（判定）」を優秀モデル（gpt-6.1-sol）で行う部分でした。高速モデル（gpt-6-luna）は料金が約20分の1です。

**高速モデルだけで精査した場合**（同じ候補を両方のモデルで判定して比較）
- 必須要件の○✕？の判定は、優秀モデルと**ほぼ完全に一致**した（103件中103件）。
- 点数の付け方は少しずれた（平均3〜4点）。上位5件の並びが入れ替わることがあった。
- 比較の基準として、優秀モデルを2回動かした場合も比べた。2回の間でも上位10件中8〜9件しか一致しないので、この程度のずれはAIの揺らぎの範囲内でもある。

**そこで精査を2段階にした（standard の既定）**
1. 高速モデル（推論 high）が、候補（提案件数×6）を求人票の全文で予備判定する。
2. 予備判定の上位（提案件数×2）だけを、優秀モデルが最終判定する。提案の点数と必須要件の判定は、すべて優秀モデルの判定を使う。

**検証**（試験DB・実モデル。候補60件すべてを優秀モデルでも判定し、提案10件を比べた・5回）
| 条件 | 提案10件の一致 | 取りこぼし | 提案の合計点の差 |
|---|---|---|---|
| 書類あり・CS志向 | 10/10 | 0件 | 0点 |
| 書類なし・CS志向（3回） | 9/10、6/10※、9/10 | 1件（78点・74点） | 0〜3点 |
| 書類あり・IT営業 | 7/10 | 3件（92点の求人が91点の求人に入れ替わり） | 3点 |

※同点の求人（69点が多数）が入れ替わっただけのもの。提案の合計点で見ると差はほぼない。

**費用（試験DB・書類あり・提案10件・一次審査400件・同じ条件で実行）**
| 構成 | 費用 | 内訳 |
|---|---|---|
| 精査をすべて優秀モデル（60件） | 約32円 | 理解2・一次審査1・精査24・推薦文5 |
| **2段階（予備60件→最終20件）** | **約19円** | 理解2・一次審査1・予備判定2・最終判定8・推薦文5 |

本番（提案20件・一次審査2,000件）の見込み: **約40円前後**（初回評価の約145円の3割弱）。

| 費用モード | 一次審査 | 候補（予備判定） | 最終判定（優秀モデル） | 精度 |
|---|---|---|---|---|
| economy | 1,500件 | 提案件数×4 | 提案件数×1.5 | 少し下がる |
| standard（既定） | 2,000件 | 提案件数×6 | 提案件数×2 | すべて優秀モデルの場合とほぼ同じ（上の検証） |
| quality | 3,000件 | 提案件数×6 | **全件**（予備判定なし・推論 high） | 最も高い |

- `HUB_AI_FINAL_FACTOR=3` のように指定すると、最終判定の件数を増やせる（`0` で全件を優秀モデル）。
- `--compare` を付けると、候補の全件を優秀モデルでも判定し、2段階にした場合と提案がどう違うかを表示する（精度確認用。費用は増える）。

1回あたりの上限: `HUB_AI_MAX_USD=0.8`（上限の85%に達したら精査を打ち切る。精度は下がる）。

## 評価コマンド（VPS）

```bash
cd /home/ubuntu/webapp/hub

# まず母集団の件数だけ確認（AIを呼ばない・無料）
node --no-warnings bin/ai-search.js --locations=東京都 --age=32 --education=大卒 --salaryMin=500 --dry

# 実行（書類は複数指定できる。種類は resume=履歴書 / cv=職務経歴書 / other）
node --no-warnings bin/ai-search.js \
  --text="顧客を長く支援する仕事がしたい。転勤は避けたい" \
  --doc=cv:/home/ubuntu/test/職務経歴書.pdf --doc=resume:/home/ubuntu/test/履歴書.pdf --names="山田 太郎" \
  --locations=東京都,神奈川県 --age=32 --education=大卒 --salaryMin=500 --features=weekend_off --top=20

# 手動検索で選んだ求人だけを審査（一次審査を飛ばして全件を精査）
node --no-warnings bin/ai-search.js --text="..." --doc=cv:... --jobs=circus:12345,hitolink:678

# 精度・件数の切り替え
#   --depth=deep        一次審査を8,000件に
#   --depth=all         条件に合う全求人を一次審査（件数が多いと時間と費用がかかる）
#   --precision=top     精査を最上位モデルで
```

| オプション | 内容 |
|---|---|
| `--text` / `--memo` | 要望・担当者メモ |
| `--doc=種類:パス` | 書類のPDF（複数可） |
| `--names` | 求職者の氏名（書類から伏せるため。AIには送らない） |
| `--locations` `--age` `--gender` `--education` `--salaryMin`（万円） | 確定条件 |
| `--employment` `--category` `--features` `--source` | 雇用形態・職種・働き方・媒体（カンマで複数） |
| `--exclude=媒体:ID,...` | 紹介済みなど、除外する求人 |
| `--jobs=媒体:ID,...` | この求人だけを審査 |
| `--conditions=条件.json` | 条件をまとめてJSONで渡す |
| `--out=結果.json` | 結果の保存先（既定は `hub/data/ai-results/`） |

結果には、提案ごとの**必須要件の判定（○×？と根拠）**、推薦理由、懸念点、応募前の確認事項、AIの元の点数と上限処理の有無が入ります。

### 個人情報の扱い
- PDFは読み取ったあと保存しません
- 氏名・住所・電話・メール・生年月日は、AIに送る前に伏せ字にします（`--names` で渡した氏名も本文から消します）
- 結果ファイルには、伏せ字にした経歴の要約だけが残ります

## 画面から使う（フェーズ2・2026-10）
トップ（`/`）を開くと、新しいAI検索の画面（`/ai`）に移動します。旧AI検索（媒体に直接ログインする方式）は `/legacy` に残しています。

### 構成
| 部品 | 役割 |
|---|---|
| webapp（3000番） | ログイン・画面・`/api/ai/*` の中継。ログインした担当者を hub-ai に伝える |
| **hub-ai（PM2・127.0.0.1:3101）** | 求職者・書類・紹介済み・AI検索の実行（同時に `HUB_AI_MAX_PARALLEL` 件まで・既定3件。超えた分は順番待ち）。サーバー内部専用 |
| 作業用DB `hub/data/workspace.sqlite` | 求職者・書類（伏せ字の本文）・紹介済み・検索条件・結果。毎晩のバックアップで7世代保存 |

### できること
- **求職者の登録**：名前を入れると番号（No.）が自動で付きます。同姓同名でも番号で区別します。名前・ふりがな・番号で呼び出せます。
- **書類**：PDFを複数登録できます。受け取ったときに文字にして、氏名・住所・連絡先を伏せてから保存します。PDFそのものは保存しません。経歴は書類が変わったときだけ作り直します（2回目以降の検索で、書類の読み取り費用がかかりません）。
- **検索**：条件と結果は求職者ごとに保存されます。呼び出すと前回の条件が入った状態になり、そのまま再検索できます。
- **紹介済み**：結果の「紹介済みにする」で記録します。次の検索から自動で除外します。
- **履歴**：全体の履歴と求職者ごとの履歴。誰が検索したかが残ります。
- **手動検索との併用**：手動検索で求人にチェックを付けて「選んだ求人をAIで審査」を押すと、その求人だけをAIが審査します。
- **画面を閉じても検索は続きます**。あとで履歴から開けます。
- **複数の担当者が同時に検索できます**。媒体にはログインしないため、検索同士がぶつかることはありません。同時に実行できる数（`HUB_AI_MAX_PARALLEL`、既定3件）を超えたときだけ順番待ちになります。
- 実行中は「経過（詳細）」に、使ったモデル・確定条件・母集団の件数・各段階の進み具合を、**経過秒数・トークン数・費用の目安**付きで表示します。
- **紹介報酬**：結果の各求人に表示します。割合は「理論年収の○%（目安 約○万円＝年収の上限×割合）」、固定は「一律○万円」。**割合が30%以上は赤で目立たせます**。ほかの媒体にも同じ求人があるときは、媒体ごとの報酬も並べて表示します（媒体で報酬が違うことがあるため）。以前の検索結果にも、求人がまだ掲載中なら表示されます。
- **並べ替え**：結果の上の「並べ替え」で、AIのおすすめ順・点数・紹介報酬（金額の目安／割合）・年収（上限／下限）の順に並べ替えられます。報酬や年収が不明な求人は最後に並びます。選んだ並べ方はブラウザに記憶されます。
- **アーカイブと削除**：担当者はアーカイブ（一覧から外す）できます。完全な削除は管理者だけができます（書類・結果もすべて消えます）。

